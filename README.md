# AISAS By ClemxyTech

AI Scouting Automation System. A shared TypeScript + Expo/React Native application for web, Android, and iOS, backed by Supabase Auth, Postgres, and an authenticated Edge Function.

## Start

```sh
npm ci
npm start         # Expo Go / native development
npm run web       # Web development with Metro
npm run build     # Production web export in dist/
npm run dev       # Serve the exported web build locally
npm run typecheck
npm test
```

The public Supabase URL and publishable key for `aisas` are included; `.env.example` documents overrides. Publishable keys are safe in clients. Database passwords, service-role keys, and integration keys must never enter this app bundle or source control.

Web visitors arrive on the branded landing page with feature showcases, an interactive sample preview, FAQs, day/night switching, and email signup. `/?signup=1` opens signup directly, `/?signin=1` opens sign-in, and `/?view=workspace` opens the app. Returning authenticated visitors and native apps go straight to the workspace. Auth and mailbox callbacks retain workspace routing.

Visitors can open a clearly labeled, device-local demo with sample businesses and `.example` email addresses. Demo scouting and campaigns never search or send. Sign in for an empty, private workspace backed by Supabase. Demo data is not uploaded into an account.

The two optional Vercel environment variables are `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`, documented in `.env.example`. The current project's public defaults are included in the app. AI, search, email-verification, and mailbox credentials stay server-side in the existing Supabase backend; the Vercel deployment serves the frontend.

After the Vercel deployment succeeds, add `aisas.clemxytech.com` under the Vercel project's Domains settings. Replace the existing `aisas` CNAME target (`custom-domains.chatgpt.site.`) in Namecheap Hosting DNS with the **exact target shown by Vercel**. Edit the existing record rather than adding a second CNAME for the same hostname. Keep the current DNS target until the Vercel deployment is ready.

For production, set the Supabase Auth **Site URL** to `https://aisas.clemxytech.com` and add `https://aisas.clemxytech.com/` to **Redirect URLs**. The backend `APP_ORIGIN` must use `https://aisas.clemxytech.com`; it was updated for this custom domain. Nylas continues to call the existing Supabase Edge Function URL, which then returns users to the custom domain. A `vercel.app` preview can display the UI and demo, but confirmation links and mailbox returns use the configured production domain.

The owner-only access policy on the existing Sites publication does not carry over to Vercel. Set Vercel's deployment access for the intended audience before sharing its URL. AISAS account authentication and database row permissions remain enforced by Supabase.

## Campaign scheduling and profile proof links

Campaign setup offers **Start when launched** or **Schedule for later**, with a calendar, hour/minute fields, AM/PM controls, and a preview showing the device time zone and offset. Selected local date/time values are stored as UTC timestamps for the existing campaign queue. Past dates/times and nonexistent daylight-saving times are rejected. Existing timestamps display in the current device time zone. Saving a schedule does not launch or approve a campaign.

Audience profiles accept optional **Video demo link** (`demo_video_url`) and **Work sample link** (`work_sample_url`). Blank values are supported for old and new profiles; supplied values are normalized to HTTP(S) web URLs. Existing profile owner permissions protect these fields. The links are never copied into the shared prospect pool.

The authenticated `sequence-writer` Edge Function loads only the caller's profile and sends the service/audience/proposition/offer and optional proof links to OpenAI. Private workspace IDs and profile metadata are excluded. Its prompt uses supplied links as supporting context in the anchor-value first message, without claiming to watch videos, inspect samples, or invent results. Links are not fetched by the endpoint. A deterministic reference block supplements the first draft if a supplied link is omitted, without duplicating links already present. The same behavior applies to demo drafts. Users continue to edit and approve all messages before launch.

Rollout order: apply `supabase/migrations/20261110223705_profile_proof_links.sql`, deploy `supabase/functions/sequence-writer` with its relative TypeScript dependencies, then deploy the frontend. The function reuses existing OpenAI configuration and the generation quota. `tests/profile-proof-rls.sql` uses rollback-only fixtures to verify defaults, owner access, URL constraints, and cross-owner isolation. `tests/campaign-schedule.test.ts` covers local/UTC conversion, midnight/noon, invalid/past values, leap years, and daylight-saving gaps. `tests/profile-proof.test.ts` covers optional fields, safe URLs, exact first-message references, and AI context privacy.

## Account password recovery

Sign-in, signup, and the new-password/confirmation fields have accessible show/hide buttons and start masked. Switching forms clears password inputs. The sign-in form includes **Forgot password?**, preserving the entered email when opening the reset request form. Reset requests return a generic account-independent message and show retry feedback for provider/rate-limit failures.

Supabase sends the reset email through the existing Auth email service and returns to the exact allowed root URL `https://aisas.clemxytech.com/`. Recovery uses the existing PKCE flow: request the link on the production website and open it in that same browser. Native apps and non-production previews open `https://aisas.clemxytech.com/?forgot=1` for browser-based recovery, so the request and callback share browser storage. No additional redirect URL, OAuth provider, or API key is required.

The client listens for `PASSWORD_RECOVERY` before the React app mounts and restores the recovery form across refreshes using an expiring user-ID marker. The marker only controls navigation. Password updates require a server-validated current user matching the recovery user and matching password confirmation. Completed recovery clears the marker and returns to the workspace; cancelling signs out the local recovery session. Expired/invalid links offer a fresh reset request. Ordinary sign-in, signup confirmation, and mailbox return routing remain supported.

`tests/auth-flow.test.ts` checks reset redirect selection, account-independent responses, provider errors, password/confirmation validation, expired and mismatched sessions, recovery marker expiration, and callback routing using mocked auth calls. Real reset email delivery is not exercised by automated tests.

## Shared Search pool

The **Search** workspace section has Companies and People modes. Company filters include company name, location, industry, company size, annual revenue and funding ranges in USD, technologies, founding-year range, domain, and keyword. People filters include name, employer, location, job title, department, seniority, industry, employer size/domain, keyword, and email/phone availability. Results are paginated in groups of 25; company cards can open a People search for decision makers at that company. Industry/seniority/department labels are categorized from available business context or job titles, rather than asserted as independent enrichment.

Every new server scouting insert with a public HTTP(S) source contributes descriptive prospect fields to `prospect_pool`. The database trigger deduplicates records across scouts and accounts. Only signed-in users can read/search it. Clients cannot insert, edit, or delete shared entries. Existing private leads are **not** backfilled: historical records do not identify which fields came from scouting versus manual edits. Demo records remain device-local and never populate the live pool.

Users can select results and save to an existing audience list or create a new one. `aisas_save_pool_prospects` runs with the caller's RLS permissions, checks ownership, and atomically copies selected rows with duplicate protection. Separate people at one company can be saved with a published phone number when email is unavailable. Copies start as new, unverified private leads; contributor identities, source list IDs/names, campaigns, suppression status, and verification history are not part of the shared schema.

The `scout-search` Edge Function handles authenticated Company/People scouting with saved, resumable runs. Users choose up to 1,000 prospects, 100 SerpAPI requests, and 1,000 public-page attempts; AI extraction defaults to 60 requests and can be raised to 1,000; **Maximum coverage** selects all maximum limits. Only records with a published email address or phone number are saved or returned in shared Search. Contactless people remain internal discovery candidates and can be enriched before saving. The target counts contact-bearing prospects. Scouts continue through query variations, named-person contact searches, regional searches for supported country-wide profiles, and provider result pagination until a target, budget, or exhausted sources stops the run. All active requests use `https://serpapi.com/search` with explicit engine parameters. Contact queries include common email providers and `"@"`; extraction accepts published addresses on any domain. Google may ignore punctuation, so `"@"` is only one signal.

New scouts first choose **Boolean Scouting** or **Google Maps Scouting**. Boolean runs use only `engine=google` and retain audience-based query variants and professional discovery. Maps runs use only `https://serpapi.com/search?engine=google_maps&type=search`; they search the audience and location as a natural Maps query. Maps defaults to saving at most 1,000 contact-bearing businesses, 100 provider requests and 1,000 public-page attempts. Maps follows canonical `start` offsets and safe next-page coordinates, including beyond 20 pages, until result exhaustion, repeated pages or the chosen request limit. Reaching the save cap does not stop Maps pagination. These limits and their credit use are visible before launch; they do not guarantee a complete inventory of every business Google knows.

Maps listings preserve place identities, so separate branches with identical names remain separate in the user's list. Public business websites and their contact pages enrich the original Maps business rather than creating records named “Contact Us.” Phone-only listings are accepted, contactless candidates remain internal, and only email/phone-bearing changes are saved and shared through the existing pool trigger. Photos, photo metadata, autocomplete, reviews, posts, and contributor-review APIs are not required for this contact-discovery workflow and are not called. New runs store their method inside the existing private checkpoint JSON; the authenticated Edge Function exposes only that method label. Older checkpoints continue to work. No new database migration or credential is required. `tests/scout-maps.test.ts` covers mode isolation, 25-page pagination, coordinate/credential handling, duplicate branches, contact gating, request limits, and website attribution.

Public source reading follows relevant team, directory, contact and listing links up to two levels. It checks robots rules and crawl delays, public DNS/IP destinations, redirects, response types and response sizes; logged-in pages, disallowed pages and access controls are not bypassed. JSON-LD Person/Organization records, microdata, scoped person cards, search snippets and optional AI extraction contribute source-backed prospects. Explicit names and AI extraction accept single names, lowercase names, initials, long names, punctuation and non-Latin scripts. AI records must contain an exact source quote identifying the name and any attributed contact details; guessed emails or expanded initials are rejected. AI extraction uses `OPENAI_API_KEY` and the chosen per-run AI request budget. Missing/failed AI is reported and structured/text extraction continues.

The UI reports search/source pages, prospects identified, duplicate merges, saved records, unavailable pages, provider requests, and stop reasons. Each short server step atomically checkpoints progress and incrementally saves/enriches the same list; a lease prevents overlapping steps. Keep AISAS open to advance automatically. Closing the app stops client-driven advancement after the active step; returning users can resume saved runs, with no new daily scout reservation. Pause takes effect after the in-flight step. No empty list is created. Only the owner's progress is readable; clients cannot mutate run state, acquire leases, or call persistence RPCs. The shared Search pool receives public results and subsequent server contact enrichment; separate people may share an office email. Private list names and run details remain private.

Deploy `supabase/migrations/20261111000848_expand_scout_coverage.sql` and `supabase/migrations/20261111074121_require_scout_contacts.sql` before the updated `scout-search` function and frontend. Include the function's `deno.json`, `import_map.json`, and relative TypeScript dependencies; the pinned `linkedom` dependency is imported through that map. `tests/scout-coverage.test.ts` covers pagination, budgets, interruption-safe state, names, source reading, source evidence and private-network/robots protection. `tests/scout-runs-rls.sql` uses rollback-only fixtures to check 125+ records, idempotent creation, leases, pause, enrichment, shared-office emails and account isolation.

Financial data, employee counts, technologies, and founding years are often absent from the current search provider results. These fields remain unavailable rather than being inferred; applying one of their filters excludes unknown records. Rich firmographic filtering requires source-backed data in those fields, such as a future enrichment-provider integration. The interface does not imply those fields are populated for every company.

Deploy `supabase/migrations/20261110210508_shared_prospect_pool.sql` before the frontend and deploy `supabase/functions/scout-search` with its bundled relative TypeScript dependencies. `tests/prospect-pool.test.ts` covers filter validation, missing-data behavior, copying, and public profile extraction; `tests/prospect-pool-rls.sql` exercises trusted ingestion/deduplication, shared reads, private copies, denied pool writes, owner isolation, and anonymous denial using rollback-only fixtures.

## On-demand email verification

Every prospect email has a **Verify** button on desktop, web, and mobile. A click checks that specific address through ZeroBounce in real time and saves the result and timestamp to the user's lead. **Verified** means the provider returned `valid`; **Invalid** means the provider returned `invalid` or the address has an obviously invalid format/reserved demo domain. Catch-all, risky, and inconclusive inboxes show **Unknown** with an explanation. Provider timeouts, missing configuration, and insufficient credits show a retry/setup error instead of falsely marking the address invalid. Verification does not send a campaign email.

Configure `aisas_ZEROBOUNCE_API_KEY` in Supabase Vault (or `ZEROBOUNCE_API_KEY` as a server-only environment variable). The existing OpenAI/SerpAPI/Nylas keys do not provide inbox verification. ZeroBounce requires an active credit balance. The verification function reads its own credential when checking an address. See the [ZeroBounce real-time validation API](https://www.zerobounce.net/docs/email-validation-api-quickstart/v2-validate-emails).

Verification uses the separate `verify-email` Edge Function; it cannot start campaigns or send email. It validates every caller with Supabase Auth before reading lead/configuration data, and uses the service-only `aisas_email_verification_key` RPC to read only the ZeroBounce credential. Gateway JWT verification is disabled because this project uses ES256 signing keys; application authentication is mandatory. Results belong to the authenticated lead owner. Clients cannot write verification fields directly; changing an email clears its previous result, and a concurrent email change prevents an in-flight result from being saved against the new address. Each user has a server-enforced limit of 200 verification attempts per UTC day. Reverify makes a fresh check. Demo mode only identifies reserved/invalid sample addresses and never claims a real inbox is verified.

`tests/email-verification.test.ts` covers positive/negative/inconclusive results, missing keys, provider failures, address mismatch, credential handling, and stale display protection. `tests/email-verification-rls.sql` checks field permissions, row isolation, and invalidation using rollback-only fixtures.

No secret values are committed to Git. Rotate these through the project's Vault dashboard. The Edge Function reads an explicit allowlist using the service-only `aisas_runtime_config` RPC and caches it for 60 seconds. Neither anonymous nor signed-in application users can call this RPC. Edge Function environment variables take precedence and remain supported for local development and alternate deployments.

For the Nylas v3 API-key flow, `NYLAS_CLIENT_SECRET` uses the same value as `NYLAS_API_KEY`. Never put integration secrets in variables prefixed with `EXPO_PUBLIC_`; those are bundled into web/native clients.

Configure the Google/Microsoft connectors needed for mailbox access and enable Yahoo/generic IMAP as appropriate. These mailbox permissions are separate from AISAS account login. 4. **Delivery worker:** apply `20261111192633_campaign_delivery_and_tracking.sql`, then deploy `campaign-dispatch`, `campaign-events`, and the updated `aisas-api`. Pixel loads only count after provider acceptance and cannot confirm a rejected or uncertain send. Privacy proxies/prefetching and disabled images affect recorded opens. Incoming messages from the sending mailbox are ignored for reply counts.

Emails sent includes accepted initial/follow-up messages; failures count failed attempts; bounce/read/response counts are unique recipients. Valid recipients means email present, not ZeroBounce verification. Duplicate inbox addresses and suppressed/known-invalid addresses are not repeatedly emailed. Unconfirmed send outcomes are kept separate and are not automatically resent. Signed events are idempotent and can reconcile events arriving before the send response. `tests/campaign-delivery.test.ts` mocks provider requests; `tests/campaign-delivery-rls.sql` uses rollback-only database fixtures and never sends mail.

## Operational details

- A paused campaign stops new dispatch attempts. A request already handed to the mail provider can finish. Pause before editing; client database grants reject edits while running/scheduled.
- `processing` recipients left by an interrupted worker and `uncertain` deliveries require administrator reconciliation with provider logs. Do not reset blindly: that could duplicate an email.
- Follow-ups stop after an inbound thread message is detected. Signed bounce and reply events stop follow-ups. An administrator can mark a lead `unsubscribed` immediately; a dedicated suppression-management UI remains a future extension.
- Completed recipients become `sent`; campaign completion is currently administrative rather than automatically inferred. Sent statistics/reporting and billing are not part of this first version.
- Native Nylas account linking finishes on the web workspace; refresh/reopen the mobile app to see new connections.
- The initial limits are 20 scouts, 100 AI sequence generations, and 20 mailbox connection attempts per user per UTC day. Failed attempts also count. Limits are enforced transactionally in private SQL.
- Before broad production use, validate provider OAuth scopes, reply/bounce behavior and a real test sequence with a mailbox you control. The current web Site is private to its owner; native distribution needs a public application hosting/auth configuration.

### Profiles, signatories and account deletion

Settings stores first/last names and a private avatar path in Supabase Auth metadata (display only). The `avatars` bucket uses owner-only policies and one-hour signed preview URLs. Expo gallery picking and JPEG processing work on web, Android and iOS; each upload is limited to 2 MB after processing. Signature images use immutable, owner-prefixed objects in the public `email-signatures` bucket so recipients can display them. Removing/replacing a signatory does not delete an image that may already be used by an approved campaign.

Audience profiles support `sender_name`, optional `signature_text`, and optional `signature_image_url`. A database trigger copies these to each campaign on save/approval; running campaigns retain their approved snapshot until paused and resaved. The delivery worker escapes all text and appends the sender, then signatory text/image to every sequence step before the tracking pixel. AI is instructed to omit signatures from the body.

`account-actions` accepts only authenticated self-deletion with the exact confirmation `DELETE` plus a freshly verified current password. It revokes refresh sessions, temporarily freezes uploads, pauses campaigns/scouts, deletes both image folders through the Storage API, disconnects exclusively owned Nylas grants, purges corresponding private email events, and deletes the Auth user. Private records cascade; the shared public-source prospect pool remains. Failed cleanup preserves the Auth account, lifts the temporary ban when possible, and reports failure; campaigns stay paused. No user ID supplied in a request can select the deletion target. The database active-account check blocks deleted accounts’ unexpired JWTs from shared pool/health reads and uploads. Emails already handed off to the provider cannot be recalled.

Validation: `npm test`, `npm run typecheck`, web/native Expo exports, Deno function checks, and rollback-only `tests/account-profile-signature-rls.sql` (fixture accounts only; no external sends).


## Ideal Prospects

**Ideal Prospects** is separate from ordinary AI Scouting. Users enter Business, Decision-maker, Starting segment, Main problem, Secondary problem, Buying triggers, and Prospecting signals. The HVAC examples are placeholders only. Users can fill all fields manually or ask AI for an editable definition after selecting an existing audience/service profile or entering a new one. Saving does not launch discovery until the user selects Boolean or Google Maps scouting and starts the qualified search.

The new `ideal_profiles` table is owner-private and ties each definition to the same owner's audience profile. A run snapshots its criteria in the existing private checkpoint JSON. AI creates niche/role/signal search terms, then the existing search and public-page reader collect candidates and bounded source excerpts. Maps can also sample up to ten relevant public reviews per listing when review signals were requested; those requests share the search-provider budget. Reviewer names are not retained. Sources retain attribution, and opinions are not represented as verified operations. Ordinary AI Scouting does not collect this extra qualification evidence or call the ideal classifier.

Only published email/phone contacts which pass evidence qualification are returned to an ideal list. A fit needs Business (25), Decision-maker (15), and Starting segment (20) verified, plus a relevant Main problem (10), Secondary problem (5), Buying trigger (10), or Prospecting signal (15), with a total of at least 70/100. Missing facts are unknown. Staffing, missed calls and buying intent are not inferred from industry, photos, general employee counts, office hours, or the user's targeting hypotheses. Each matched/mismatched judgment requires a verbatim quote from an actual collected source; scores and eligibility are recomputed in code, not accepted from model output. This is evidence-based AI assessment, not a guarantee of accuracy, demand, or purchase. Narrow criteria may return zero qualified contacts. Users can inspect every returned qualification and source.

Run progress distinguishes analyzed candidates, qualified contacts, missing evidence and rejected fits. Each short step either discovers, gathers reviews, or assesses up to three candidates. The AI budget covers qualification requests; a new search also uses one AI planning request. Provider failures stop qualification with resumable progress, never fall back to saving unqualified leads. Only qualified business/contact fields enter the existing shared prospect pool. `ideal_qualifications` reports, target definitions, source excerpts and campaign context stay private.

AI campaign drafting uses the selected service profile and ideal criteria on the selected owned audience list. The `{{ideal_observation}}` token inserts a different verified, attributed quotation for each qualified recipient. Potential needs remain conditional. Recipient previews allow review before approval. Campaign recipient insertion snapshots the private qualification; the existing guarded delivery RPC returns that frozen context, so later report edits cannot change a launched recipient's observation. Existing messages and signatories continue through the same delivery pipeline.

Apply `20261112163237_ideal_prospect_qualification.sql` `20261112165556_ideal_report_owner_guards.sql`, and `20261112170539_ideal_lead_owner_index.sql`, deploy `ideal-prospects`, `scout-search`, `sequence-writer`, `aisas-api`, `campaign-dispatch`, and `campaign-events` with their relative dependencies/import maps, then publish the frontend. The existing OpenAI and SerpAPI keys are reused; no new credentials are needed. `tests/ideal-prospects.test.ts`, `tests/ideal-sequence.test.ts`, and rollback-only `tests/ideal-prospects-rls.sql` cover grounding, eligibility, context isolation, checkpoints, owner relationships, private evidence, recipient snapshots, and account-deletion cascades.
